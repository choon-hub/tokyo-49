# tokyo-49 GitHub Issue 分割設計書

対象: 要件定義書 v0.2（2026-10-12）
目的: 機能単位・revert 可能な最小単位の GitHub issue に分割する。各 issue をもとに、後続の設計 skill が「受け入れ要件・実装設計 issue」を作成する。

---

## 1. 分割方針

| 方針 | 内容 |
|---|---|
| 1 issue = 1 revert 単位 | その issue の PR 1本を revert しても、アプリが起動し、他の機能が壊れない |
| 縦割り（ユーザー価値）優先 | 画面だけ・DB だけの issue は避ける。ただしデータ生成系は独立した issue とする |
| 企画者目線 | issue には「何ができるようになるか」を書く。コード構造・ファイル構成・テスト設計は書かない（設計 skill に委ねる） |
| テスト | 各 issue には含めない。テスト設計は実装設計 issue で扱う |
| 受け入れ要件 | 書かない。ただし「完了イメージ」を1〜3行で添える（設計 skill への入力） |
| 未決事項 | 暫定案で進め、各 issue の「確認事項」に明記する |

### revert 可能性のルール
- 後続 issue が前提とする機能は、必ず「依存」に明記する。
- revert 時に壊れる後続 issue は、先に revert する（依存の逆順）。
- ユーザーデータ（visits）の形を変える issue は、本計画では T-04 のみ。以降はデータ形式を変えない。

### Phase 0: 基盤

#### T-01 アプリの土台（起動・縦固定・日本語・アプリ名）
- **概要**: Android 端末で起動でき、ホーム画面（中身は空でよい）が表示される。
- **要件**
  - アプリ名は「tokyo-49」
  - 画面は縦固定
  - 表示言語は日本語のみ（多言語対応なし）
  - 対象は Android スマホ。最低 OS は指定せず、Expo の既定に従う
  - 通信を一切必要としない（外部サービス・API に依存しない）
- **完了イメージ**: 端末にインストールして起動すると、縦固定のホーム画面が出る。
- **スコープ外**: テーマ、データ保存、各機能
- **依存**: なし
- **確認事項**: applicationId は暫定値のまま進める（確定は T-29）
- **参照**: §1.2, §3

#### T-02 ライト／ダーク対応（共通テーマ）
- **概要**: 端末のシステム設定に追従して、アプリ全体がライト／ダークで切り替わる。
- **要件**
  - 手動切り替えは設けない（システム設定にのみ追従）
  - 共通の文字色・背景色・ボタン色などをライト／ダークで定義する
  - どちらのテーマでも文字が読める
- **完了イメージ**: 端末のダークモードを切り替えると、アプリの配色が即座に変わる。
- **スコープ外**: 地図の専用パレット（T-24）
- **依存**: T-01
- **参照**: §1.2, §2.4, §3

#### T-03 49区市マスタと一覧タブ
- **概要**: ホームに「一覧」タブが表示され、東京23区＋26市の計49区市が確認できる。
- **要件**
  - 対象は 23区＋26市のみ。町・村・島しょ部は含めない
  - 各区市は名称・読み・区／市の種別・コード（JIS）を持つ
  - ホームは「地図」「一覧」のタブ構成にする（地図タブは枠のみ、中身は T-20）
  - 制覇数は「0 / 49」と表示する
- **完了イメージ**: 一覧タブに49区市が並び、「0 / 49」が見える。
- **スコープ外**: 訪問済みの表示（T-05）、タップ時の動作（T-06）
- **依存**: T-01
- **確認事項**: マスタは固定データとして持つ。後に辞書ビルドスクリプトが出力する定数（§4.2）と内容を一致させる必要がある
- **参照**: §1.1, §2.4, §4.2, §7

### Phase 1: 訪問記録

#### T-04 区市を直接選んで訪問を記録する
- **概要**: 区市を選び、訪問日・メモを入力して訪問を1件保存できる。アプリを再起動しても残る。
- **要件**
  - ホームから「訪問を記録」に進める
  - 区市を直接選択できる（49区市から選ぶ。この導線は以降も常に残す）
  - 区市のみを選んだ場合、場所名には区市名が自動で入る
  - 訪問日の初期値は今日（端末のローカル日付）。過去日・未来日とも指定可。日付不明は不可（必須）
  - メモは任意
  - 保存は確認ダイアログなしで即時反映
  - 1訪問＝1行で記録する。同じ区市を何度でも記録できる
  - 訪問の記録（ユーザーデータ）は、辞書データと別の保存領域に分けて持つ
- **完了イメージ**: 区市を選んで保存し、アプリを再起動してもデータが失われない。
- **スコープ外**: 一覧への反映（T-05）、駅・町域の入力（T-14〜）、編集・削除
- **依存**: T-03
- **確認事項**: 未来日の訪問も「訪問済み」として扱う（要件書どおり。制覇数にも含まれる）
- **参照**: §2.1(5,7,8), §2.3, §5.2

#### T-05 一覧に訪問済みと制覇数 / 49 を反映する
- **概要**: 訪問を記録した区市が、一覧上で訪問済みと分かる。制覇数が更新される。
- **要件**
  - 訪問履歴が1件以上ある区市を「訪問済み」とする（履歴から導出。別フラグは持たない）
  - 履歴をすべて削除した区市は未訪問に戻る
  - 制覇数 / 49 のみを表示する（区／市部の内訳、訪問回数ランキングは出さない）
- **完了イメージ**: T-04 で記録した区市にチェックが付き、「1 / 49」になる。
- **スコープ外**: 地図への反映（T-20）
- **依存**: T-04
- **参照**: §2.3, §2.4, §5.2

#### T-06 区市ボトムシートで訪問履歴を見る
- **概要**: 一覧の区市をタップすると、その区市の訪問履歴がボトムシートで見られる。
- **要件**
  - シートに区市名と、訪問履歴（場所名・訪問日・メモ）を表示する
  - 未訪問の区市でも同じシートが開く（履歴は空）
  - 全履歴を横断して見る画面は設けない
- **完了イメージ**: 一覧から区市をタップすると、履歴が日付付きで確認できる。
- **スコープ外**: 追記・編集・削除、地図からの起動（T-21）
- **依存**: T-05
- **参照**: §2.3, §2.4, §7

#### T-07 ボトムシートから訪問を追記する
- **概要**: ボトムシート内で、その区市の訪問を追記できる。
- **要件**
  - 追記ボタンから、場所名・訪問日・メモを入力して保存する（区市は確定済みのため選択不要）
  - 訪問日の初期値は今日。確認ダイアログなしで保存
  - 未訪問の区市でも追記できる
- **完了イメージ**: 未訪問の区市のシートから追記すると、訪問済みになり制覇数が増える。
- **依存**: T-06
- **参照**: §2.4

#### T-08 訪問履歴を編集する
- **概要**: ボトムシートの各履歴を編集できる。
- **要件**
  - 編集できる項目は場所名・訪問日・メモ
  - 区市と入力経路は変更できない（誤りは削除して再登録）
  - 保存は確認ダイアログなしで即時反映
- **完了イメージ**: 履歴の場所名・日付・メモを変更して保存すると、シートに反映される。
- **確認事項**: Q20（暫定）。区市変更を可とする場合は、入力経路・辞書 ID の扱いを別途決める必要がある
- **依存**: T-06
- **参照**: §2.3, §10 Q20

#### T-09 訪問履歴を削除する
- **概要**: ボトムシートの各履歴を削除できる。
- **要件**
  - 確認ダイアログなしで即時削除。取り消し（Undo）はできない
  - 区市の履歴が0件になったら、未訪問に戻る
- **完了イメージ**: 唯一の履歴を削除すると、区市が未訪問に戻り制覇数が減る。
- **確認事項**: 誤削除のリスクあり（§11）。気になる場合は、スナックバーでの Undo を別 issue として後から追加できる
- **依存**: T-06
- **参照**: §2.3, §11

### Phase 2: 辞書データ

#### T-10 辞書の同梱と版更新の仕組み
- **概要**: 駅・町域の辞書をアプリに同梱し、アプリ更新時に新しい版へ入れ替えられる。
- **要件**
  - 辞書は事前に作成したものをアプリに同梱する（実行時に生成・通信しない）
  - 辞書には版を持たせる。アプリ起動時、同梱版が端末内の版より新しければ辞書を丸ごと入れ替える
  - 辞書の入れ替えで、ユーザーの訪問データには一切触れない
  - この issue 時点の辞書は空（または最小）でよい
- **完了イメージ**: 辞書の版を上げてアプリを更新しても、訪問履歴は残ったまま辞書だけ更新される。
- **スコープ外**: 実データの投入（T-11, T-12）
- **依存**: T-01
- **参照**: §3, §4.2, §5

#### T-11 駅辞書データの生成・同梱
- **概要**: 駅名と所在区市を引ける辞書データを、ビルド時のスクリプトで生成して同梱する。
- **要件**
  - 出典は国土数値情報 N02（駅）と N03（行政区域）。駅の代表点から区市を判定する
  - 駅名と所在地が一致しない駅（例: 目黒駅＝品川区）は、駅データの所在地を正とする
  - 事業者違いの同名駅（新宿＝JR・京王・小田急ほか）は、同一区市なら1件に統合する
  - 区境をまたぐ駅（例: 新宿駅）は、手動補正ファイル（駅名→区市コード）で1つに確定する
  - 都内の49区市に属する駅のみを対象とする
  - 生成は再実行でき、手動補正は補正ファイルに集約する
- **完了イメージ**: スクリプトを実行すると、駅名・区市コード・路線表示用の情報を持つ辞書が出力され、同梱される。
- **スコープ外**: 駅の読み（T-13）、検索 UI（T-14）
- **依存**: T-10
- **確認事項**: データの出典ライセンス（国土数値情報）の利用条件は、実装時に確認する
- **参照**: §2.2, §4.1, §4.2, §5.1

#### T-12 町域辞書データの生成・同梱
- **概要**: 町域名・読みと所在区市を引ける辞書データを生成して同梱する。
- **要件**
  - 出典は日本郵便 KEN_ALL。49区市に属する町域のみを対象とする
  - 「以下に掲載がない場合」などのノイズ行を除去する
  - 町域名＋区市コードで重複を排除する
  - 複数の区市に同名の町域がある場合（例: 本町）は、区市ごとに別の行として持つ
- **完了イメージ**: 「西新宿」が新宿区として、「本町」が複数区市の候補として辞書に入っている。
- **依存**: T-10
- **参照**: §2.2, §4.1, §5.1

#### T-13 駅の読みデータ補完
- **概要**: 駅辞書に読み（ひらがな）を付与する。
- **要件**
  - 国土数値情報 N02 には駅の読みがないため、別データで補完する（候補: 駅データ.jp など）
  - 補完データを使う前に、ライセンスと収録項目を確認する
  - 読みが付与できなかった駅は、読み検索の対象外でよい（名前検索には影響させない）
- **完了イメージ**: 駅辞書の各駅に読みが入っている。
- **確認事項**: **ライセンス未確認**（§11）。利用不可だった場合の代替（読み検索を町域のみとする、手動で読みを付けるなど）は、確認結果を見て決める。この issue は他の issue をブロックしない（T-16 のみ依存）
- **依存**: T-11
- **参照**: §4.1, §11

### Phase 3: 候補検索

#### T-14 駅名の候補表示と区市の確定
- **概要**: 訪問入力で駅名を入力すると、駅の候補が区市付きで表示され、選ぶと区市が確定する。
- **要件**
  - 入力欄に自由テキストを入力できる。末尾の「駅」付きも可
  - 入力に応じて、駅名の**前方一致のみ**で候補を即時表示する（部分一致はしない）
  - 表示形式は `上野駅（台東区）`
  - 候補を選ぶと区市が確定し、場所名・日付・メモの入力に進める
  - 区市の直接選択導線（T-04）は残す
  - 辞書にある駅名の表記ゆれ（ヶ／ケなど）の追加正規化は行わない
- **完了イメージ**: 「うえの」ではなく「上野」と入力すると、「上野駅（台東区）」が候補に出て、選べる。
- **スコープ外**: 町域（T-15）、読み入力（T-16）、30件超（T-17）、候補なし（T-18）
- **依存**: T-04, T-11
- **参照**: §2.1(1〜3), §6

#### T-15 町域名の候補を追加する
- **概要**: 候補に町域名が加わる。
- **要件**
  - 表示形式は `西新宿（新宿区）`
  - 駅の候補を町域より先に並べる
  - 町域を選んだ場合の場所名は町域名のみ（例: 西新宿）。区市は別に表示する
  - 同名の町域が複数の区市にある場合は、区市名を併記した候補から選ばせる
- **完了イメージ**: 「本町」と入力すると、区市名つきの本町が複数並ぶ。
- **依存**: T-14, T-12
- **参照**: §2.1(2), §2.2, §9 Q6/Q18

#### T-16 読み（ひらがな・カタカナ）での検索
- **概要**: ひらがな・カタカナでの入力でも、駅・町域の候補が出る。
- **要件**
  - ひらがな・カタカナ・漢字のいずれの入力でも同じ候補が出る
  - 全角・半角の違いは吸収する
  - 前方一致のみ。部分一致は行わない
- **完了イメージ**: 「しんじゅく」「シンジュク」「新宿」のどれでも新宿の候補が出る。
- **確認事項**: 駅の読みはライセンス確認（T-13）の結果に依存。駅の読みが使えない場合は、町域のみ読み検索に対応する暫定扱いとする
- **依存**: T-15, T-13
- **参照**: §2.1(1), §6

#### T-17 候補の上限30件と「他N件」表示
- **概要**: 候補が多い場合に30件までを表示し、残り件数を「他N件」と示す。
- **要件**
  - 候補は最大30件表示する
  - 30件を超える場合は、末尾に「他N件」（N＝全ヒット件数−30）を表示し、入力の絞り込みを促す
  - 「他N件」はタップできなくてよい（表示のみ）
- **完了イメージ**: 「あ」と入力すると、30件と「他N件」が表示される。
- **依存**: T-15
- **確認事項**: 「他N件」のタップ動作は要件書に記載がないため、表示のみとする暫定扱い
- **参照**: §2.1(2), §6

#### T-18 辞書にない入力（施設名・都外）の扱い
- **概要**: 辞書にヒットしない入力でも、場所名として保持し、区市を手動で選んで記録できる。
- **要件**
  - 施設名など、辞書にヒットしない入力は、入力した文字列をそのまま場所名として使い、区市を手動で選択させる
  - 都外の駅など辞書にない入力は「候補なし」と表示し、区市の直接選択へ誘導する（都外であることは明示しない）
  - 区市未確定のまま下書き保存はできない
- **完了イメージ**: 「東京ドーム」と入力して「文京区」を選ぶと、場所名「東京ドーム」・文京区で保存できる。
- **依存**: T-14
- **確認事項**: 施設名の命中率が低く、常に手動選択になる点は運用で許容する（§11）
- **参照**: §2.1(4,6), §11

### Phase 5: データ引き継ぎ

#### T-25 設定画面（隠し導線）
- **概要**: 通常の UI には出ない、設定画面への入口を作る。
- **要件**
  - 設定画面は、通常の操作では目に入らない導線で開く
  - 設定画面の中身は、エクスポート／インポートのみ（T-26 以降で追加）
- **完了イメージ**: 決められた操作をすると設定画面が開く。通常の画面には設定ボタンがない。
- **確認事項**: **隠し導線の具体的な操作が未定**（例: タイトルの長押し、設定アイコンを奥の画面に置く等）。要件書は「設定画面の奥または隠し導線」としか書いていない。暫定案: ホームのタイトル部分の長押し
- **依存**: T-01
- **参照**: §2.5, §7

#### T-26 JSON エクスポート
- **概要**: 訪問履歴を JSON ファイルとして書き出せる。
- **要件**
  - 形式は要件書 §2.5 のとおり（version=1、exportedAt、visits）
  - 辞書は同梱のため対象外
  - 全訪問履歴が出力される
- **完了イメージ**: 設定画面から書き出した JSON を、別の端末へ持ち出せる。
- **確認事項**: **書き出し先・受け渡し方法が未定**（端末内に保存／共有メニュー等）。暫定案: Android の共有機能で任意のアプリ・保存先に渡す
- **依存**: T-04, T-25
- **参照**: §2.5

#### T-27 JSON インポート（検証＋マージ）
- **概要**: エクスポートした JSON を読み込み、既存の履歴に追加できる。
- **要件**
  - 検証は次のとおり。1件でも不正があればファイル全体を拒否し、最初の不正箇所を表示する。データは一切変更しない
    - version が 1
    - visits が配列で、各要素に必須項目（placeName / municipalityCode / source / visitedOn）がある
    - municipalityCode が49区市のコードに含まれる
    - source が station / town / manual のいずれか
    - visitedOn が実在する YYYY-MM-DD
    - memo が文字列または null
  - 検証通過後、取り込み前に確認ダイアログを出す（破壊的操作のため、この確認は残す）
  - マージは追加のみ。重複判定キー（場所名＋区市コード＋訪問日）が既存と一致する行はスキップする
  - 取り込みは全件成功か全件失敗かのどちらか（途中で失敗したら元に戻る）
- **完了イメージ**: 別端末のエクスポートを取り込むと、重複なく履歴が追加される。不正なファイルは理由つきで拒否される。
- **確認事項**: 取り込み結果（追加N件・スキップN件）の表示は要件書にないが、暫定で表示する。ファイルの選び方（ファイル選択画面）も暫定で標準の選択画面とする
- **依存**: T-26
- **参照**: §2.5

#### T-28 JSON インポート：上書きモード
- **概要**: インポート時に、マージではなく「上書き」を選べる。
- **要件**
  - 取り込み前の確認ダイアログで、マージか上書きかを選ばせる
  - 上書きは、既存の訪問履歴をすべて削除してから取り込む
  - 全件成功か全件失敗かのどちらか。失敗時は元の履歴が残る
  - 上書きが破壊的であることを、ダイアログで明確に示す
- **完了イメージ**: 上書きを選ぶと、履歴が取り込んだファイルの内容だけになる。
- **依存**: T-27
- **参照**: §2.5

### Phase 6: 配布

#### T-29 配布準備（applicationId 確定・署名鍵・APK）
- **概要**: 個人利用の APK を、更新可能な形で配布できる状態にする。
- **要件**
  - applicationId を確定する。確定後は変更しない
  - 署名鍵を用意し、必ず保管する
  - APK を直接インストールして使える
- **完了イメージ**: APK を端末にインストールでき、同じ署名で上書き更新してもデータが残る。
- **確認事項**: **Q21（暫定: com.tokyo49.app）**。アプリ名の「tokyo-49」にハイフンが含まれるが、Android の applicationId にはハイフンが使えない。署名鍵と applicationId が変わると、上書きインストールもデータ引き継ぎもできなくなる（§11）
- **参照**: §1.2, §8-9, §10 Q21, §11
